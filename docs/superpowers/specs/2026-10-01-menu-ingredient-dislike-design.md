# 生成メニューの材料から苦手を登録する設計

- 日付: 2026-10-01
- 状態: **人間レビュー待ち**
- 対象: 家族向け献立の結果画面と履歴詳細。料理ごとの材料行から、既存の `member_dislikes` へ苦手を追加・削除する
- 種別: 登録の入口を足す。保存先、生成、再確認の規則は変えない
- 実装が正: 本書は未実装の設計。数値・関数名・文言は 2026-10-01 時点のコードに合わせた

---

## 1. 結論

生成した献立と、あとから開く履歴の、**料理ごとの材料**に「苦手」を付ける。押すと画面中央の確認ダイアログが開き、短い食べ物名と、登録完了の家族を複数選んで保存する。

保存先は設定画面の「苦手食材」と同じ `public.member_dislikes` である。今見ている献立の本文は書き換えない。次に作る献立から、その苦手を避ける。

保存した名前が、その献立を作ったときの苦手と違うとき、既存の再確認が「好みが変わった」と判断し、**材料と手順を画面から隠す**。料理のデータは残る。この規則（HR2）は変えない。ダイアログは保存前にそのことを書く。

## 2. 目的と対象外

### 2.1 目的

食べられないわけではないが苦手な食べ物を、家族ごとに残す。設定画面へ先に行って自由入力しなくても、目の前の材料から登録できるようにする。

### 2.2 この設計でやること

- 家族向けの生成結果と履歴詳細で、選択中の料理の材料ごとに「苦手」を出す
- 名前を確認し、登録完了の家族へ複数同時に付ける、外す
- 設定画面と同じ追加・削除と、同じ保存後の再確認を使う

### 2.3 対象外

- アイデア献立。家族の苦手を生成に使わないため、ボタンを出さない
- 買い物用の材料まとめ（献立全体で食材を1行にまとめた一覧）
- 週献立や緊急献立の独自画面。既存の献立詳細（`MenuResult`）を開いたときだけ、この設計のボタンが出る
- 今の献立の作り直し、本文の書き換え、生成時の「苦手の希望について」の再計算
- `isRevalidationBodyVisible` と `preference_changed` の意味の変更
- アレルギー、好みの学習（taste signals）、プライバシー文の版
- データベースのマイグレーション、新しい RPC、生成プロンプト、Netlify Function
- 「ピーマン」と「ぴーまん」を1つにまとめること
- 設定画面の苦手食材フォームの見た目の変更
- 新しい E2E
- 食材名や家族名のログ出力

## 3. 画面

### 3.1 材料の行

対象は `MenuDishes` の、選択中の料理の材料である。行の2列（名前 / 分量）は維持する。ボタンは名前の側、材料名と「ラベル確認」バッジの下に置く。

- 見える文字は「苦手」
- アクセシブル名は「{材料名}を苦手に登録」
- 押せる範囲は 44×44 CSS px 以上
- 320 CSS px 幅で横スクロールを出さない。長い名前は折り返す

ボタンの下には、その材料名と同一の苦手を既に持つ人の表示名を、設定と同じ順で「・」区切りで出す。一致する人がいなければ、この行は出さない。折返しはしてよい。

表示名は設定と同じ規則にする。`display_name` を `trim` し、空なら「名前未設定」。

### 3.2 ボタンを出す条件

次をすべて満たすときだけ出す。

1. 献立のモードが `household` である。`idea` ではコールバックを渡しても出さない
2. 家族一覧が次のどちらかである
   - 成功し、`status === "complete"` の人が1人以上いる
   - 失敗した
3. 献立詳細が材料を描いている。好みの変化で本文が隠れているあいだは、材料が無いのでボタンも無い

家族一覧の読み込み中は出さない。成功して登録完了の人が0人のときも出さない。失敗したときは出す。ダイアログで「家族情報を読み込めませんでした」と見せ、保存はできない。

苦手一覧は、ボタンを出す条件に含めない。読み込み中と失敗のときは、ボタン下の名前を出さない。ダイアログでは、読み込み中は保存できず、失敗したら「苦手食材を読み込めませんでした」と出して保存できない。

### 3.3 確認ダイアログ

再生成と同じ native `<dialog>` の中央ダイアログにする。下から出るシートにはしない。クラスは既存の `history-dialog` に合わせる。

ダイアログの状態は `household-menu-detail-body` が持つ。`gateOpen` の内側（`MenuResult`）には置かない。再確認で材料一覧が消えても、保存の途中でダイアログが消えないようにするためである。

| 要素 | 文言・動き |
| --- | --- |
| タイトル | 苦手な食べ物 |
| 入力ラベル | 食べ物の名前 |
| 初期値 | 押した材料の `name` |
| 補助文 | 短くすると、次の献立で見つかりやすくなります。名前を変えると新しい苦手として追加し、前の名前は設定に残ります。 |
| 家族の見出し | 苦手な人 |
| 家族 | 登録完了の人だけ。`listHouseholdMembers` の順（`sort_order`、次に `created_at`） |
| 初期チェック | 開いたときの名前と同一の苦手を、既に持つ人 |
| 注意 | 保存すると、この献立は今の苦手と違うため、料理の手順は閉じます。次に作る献立から避けます。食べられないものの登録ではありません。 |
| 主ボタン | 保存する。送信中は「保存しています」とし、入力とボタンを止める |
| 副ボタン | キャンセル |

送信中は Escape と背面クリックでも閉じない。送信中でなければ、キャンセル、Escape、背面クリックは書き込まずに閉じる。再生成ダイアログと同じく、native の即時 close は止めて親が閉じる。

差分が無いとき、名前が空のとき、正規化後 81 文字以上のとき、家族または苦手の読み込みに失敗しているとき、送信中は、保存できない。

81 文字以上のときは入力の直下に「苦手食材は1〜80文字で入力してください」を出す。空のときはこの文を出さず、保存できない状態だけにする。

## 4. 名前の同一性と保存差分

### 4.1 同一性

追加関数 `addMemberDislike` が保存前に行うのと同じ正規化を使う。

1. `normalize("NFKC")`
2. `trim`
3. 比較と重複判定だけ `toLowerCase()` する

データベースの一意制約は `member_dislikes_name_unique`（`member_id`, `lower(btrim(ingredient_name))`）である。文字数制約は `char_length(btrim(ingredient_name))` が 1〜80 である。

`normalizeFoodText` は使わない。かなの折りたたみや句読点の除去は、献立文の中から苦手を探す既存の処理に残す。登録の同一性には使わない。したがって「ピーマン」と「ぴーまん」は別の行のままである。次の献立で両方とも見つかる動きは、今の生成と soft gap のままである。

正規化後の長さは、既存の `addMemberDislike` と同じく JavaScript の `string.length`（UTF-16）で見る。

### 4.2 保存する差分

保存対象は、フィールドにある**今の名前**だけである。ダイアログを開いたときの名前の同一性を `openedIdentity`、フィールドの今の同一性を `currentIdentity` と呼ぶ。

チェックは、名前を編集しても自動では変えない。開いたときのチェックから、利用者が付け外したものだけが変わる。

各登録完了メンバーについて、次だけを行う。

- チェックがあり、その人が `currentIdentity` を持っていない → `addMemberDislike`
- チェックが無く、その人が `currentIdentity` を持っていて、`currentIdentity === openedIdentity` → その行を `deleteMemberDislike`
- 名前を変えている（`currentIdentity !== openedIdentity`）ときの未チェック → 追加も削除もしない

名前を変えてチェックを残した人には、新しい名前を追加する。前の名前の行は残る。名前を変えただけで、別の名前を削除することはない。

チェックを開いたときの名前のまま外すと、その名前の行だけを削除する。

差分が1件も無いときは保存できない。

### 4.3 書き込み順と失敗

メンバー順に1人ずつ行う。

- 一意制約で追加が失敗したときは、その人の苦手を読み直す。`currentIdentity` が既にあれば、その人は成功として次へ進む。無ければそこで止める
- その他の失敗では止める。ダイアログは開いたままにする
- 止めたときは、設定画面と同じく、`Error` ならその `message` を出す。`Error` でないときは、追加なら「苦手食材を追加できませんでした」、削除なら「苦手食材を削除できませんでした」
- この操作の `insert` または `delete` が1件以上成功したあとに止めたときは、同じ alert に「一部は保存済みです。チェックを確認して、もう一度保存してください。」を足す。読み直して既に存在しただけだった人は、この文の条件に数えない
- 止めたあとは、開いているダイアログのチェックを、今の名前についてサーバにある人だけに合わせる。まだ保存していないチェックは戻る。読み直しに失敗したら、チェックは触らず、読み込み失敗の文言を足す

家族一覧の失敗文言は「家族情報を読み込めませんでした」。苦手一覧の失敗文言は「苦手食材を読み込めませんでした」。どちらも既存の API 文言である。

全員が成功したらダイアログを閉じる。成功には、一意制約のあと読み直して既に存在した人を含む。

### 4.4 保存後の再確認

この操作で `insert` または `delete` が1件でも成功したら、設定画面と同じ `invalidateHouseholdSafetyDependents` を呼ぶ。部分的に止まったときも呼ぶ。一意制約のあと読み直して、既に存在しただけだった人はコミットに数えない。コミットが0件なら呼ばない。

この関数は苦手の query、献立結果、履歴、再確認、買い物、週献立、緊急献立の cache を無効化し、他タブへ家族設定の変更を知らせる。`member_dislikes` の Realtime も、既存どおり履歴の hard 再確認を始める。どちらも止めない。

再確認の呼び出しが成功し、全員の保存も成功したときの status は次のどれかである。

- 追加だけで削除が無い: 「{正規化後の名前}を苦手に覚えました」
- 削除だけで追加が無い: 「{正規化後の名前}の苦手を外しました」
- 追加と削除が両方ある: 「苦手を更新しました」

再確認の呼び出しだけが失敗し、保存は全員成功したときは、短い完了文は出さない。設定画面と同じ次の文だけを status に出す。ダイアログは閉じる。

「家族設定を保存しました。画面の再確認に失敗したため、献立・履歴を開き直すか再読み込みしてください。」

部分的に止まった状態で再確認の呼び出しも失敗したときは、ダイアログを閉じない。§4.3 の alert に、上の再確認失敗の文を足す。

完了文と再確認失敗文は、再確認バナーとは別の `role="status"` に出す。再確認が「確認しています」に進んでも、この文は残してよい。食材名と家族名はログに出さない。新しいログキーは足さない。

### 4.5 保存したあとの献立画面

献立本文と、生成時の「苦手の希望について」は、この保存では書き換えない。後者は献立に保存された `preference_snapshot` の苦手から計算している。

苦手の追加・削除は、再確認では食べる量・辛さ・食べやすさと同じ `preference_changed` になる。`isRevalidationBodyVisible` は `preference_changed` のとき本文を隠す（HR2）。結果画面でも履歴詳細でも、保存のあと材料と手順が隠れることがある。確認中は「この献立の対象家族の設定で確認しています」、確認後は「この献立の対象家族の設定で確認しました。作成時から条件が変わっています」と「好みの設定が変わっています」になる。これは設定画面から苦手を変えたときと同じである。

隠れたあとに材料から登録することはできない。設定画面の苦手食材は、これまでどおり使える。

## 6. テスト

新規の E2E は足さない。設定画面の既存の苦手追加シナリオは変更しない。

### 6.1 同一性

- NFKC と前後の空白を除いたあと、大文字小文字を除いて同じなら一致する
- 「ピーマン」と「ぴーまん」は一致しない
- 正規化後 0 文字は保存不可。81 文字以上は保存不可。80 文字は保存可

### 6.2 ダイアログ

- 初期値は材料名。既にその名前を持つ人はチェック済み
- 名前を変えて保存すると、チェックした人へ新しい名前を追加し、前の名前は削除しない
- 名前を変えた状態の未チェックは、その人が新しい名前を既に持っていても削除しない
- 名前を変えずにチェックを外すと、その名前だけを削除する
- 差分が無い、空、81 文字以上では保存できない
- 追加または削除が失敗してもダイアログは開いたままである
- 一部成功のあと失敗すると、成功分を残し、部分保存の文を出す
- 送信中はキャンセルできない

### 6.3 材料行

- `household` でコールバックがあるとき、「ピーマンを苦手に登録」として押せる
- コールバックが無いとき、および `idea` のときはボタンが無い
- 登録済みの名前は、同一性の一致する人だけ出る
- 幅 320px で材料行が横にはみ出さない

### 6.4 保存の接続

- 成功時に `addMemberDislike` / `deleteMemberDislike` と `invalidateHouseholdSafetyDependents` を呼ぶ
- コミットの前に失敗したときは `invalidateHouseholdSafetyDependents` を呼ばない
- 1件コミットしたあとに失敗したときは、ダイアログを開いたまま `invalidateHouseholdSafetyDependents` を呼ぶ
- 再確認の呼び出しだけが失敗したときは、ダイアログを閉じ、§4.4 の再確認失敗文を出す
- アイデア献立の詳細にはボタンが無い
- 登録完了の人が0人のときはボタンが無い

再確認の判定、プロンプト、`preference_snapshot`、設定画面の既存テストの期待は変えない。

## 7. 受け入れ条件

- 家族向けの生成結果と履歴詳細で、料理の材料から苦手を登録・削除でき、設定の苦手食材と同じ行になる
- アイデア献立と材料まとめには操作が無い
- 今の献立の本文は変わらない
- 保存後、既存の再確認が好みの変化として本文を隠すことがある。ダイアログがそのことを先に書く
- アレルギー、好みの学習、プライバシー文、生成関数、データベーススキーマは変わらない
- 食材名と家族名がログに出ない
