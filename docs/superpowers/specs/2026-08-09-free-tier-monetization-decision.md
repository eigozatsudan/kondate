## 結論

無料ユーザーを含む事業の**主収益は Plus** とする。ただし現行の価格・上限（月額 580 円 /
1 日 10 回）が採算に合うかは未検証であり、**Plus 増分 AI 原価の実測結果によっては、価格、
上限、または課金モデルそのものを変更する**。

現時点では、次を採用しない。

- 広告配信スクリプトの導入
- スポンサーによる献立内容への介入
- 広告収益を目的とする公開 SEO 面の新設

成果報酬リンク（Amazon / 楽天）は、**保留（現時点不採用）** とする。買い物文脈との親和性
はあるが、収益上限の桁が実装・法務・運用コストに見合う見込みが立たず、候補面
`/shopping` が認証必須であるという媒体資格 blocker も未解消であるため、検討を継続する
だけでも工数を誘発する。復活条件は §2.2 に定める。任意の単発支援は、利用継続を支える
補助的な選択肢にとどめる。

本書が決めるのは**実装開始ではなく、次に何を計測して判断するか**である。以下では、
確認済みの事実を「事実」、まだ根拠がない見通しを「推測」、人間または規約確認が必要な
事項を「要確認」と明記する。

## 0. 判断のアンカー（要決定・最優先）

本書の初版には収益目標が無く、そのため各ゲートの閾値を校正できなかった。以下を人間が
先に定める。仮の数値でよい。目標のない閾値は後から気分で決まる。

- **収益目標（要決定）**: いつまでに、月次いくらの純寄与を得るか。最低ラインの目安は
  「OpenRouter 変動費を賄う」。
- **現在の規模（要確認・最重要の欠落）**: MAU、Free 上限到達者数、継続利用者数。
  この桁が分からないまま KPI の精緻さを決めることはできない。3 桁前半なら、cohort
  単位の転換率・継続率は信頼区間が広すぎて意思決定に使えず、計測設計の精緻化は過剰
  投資となる。**Step 0 で確認し、その結果に応じて §3 の計測範囲を縮小してよい。**

## 1. 現状

### 1.1 確認済みの製品条件（事実）

- Free の献立生成成功上限は **1 日 3 回**、Plus は **1 日 10 回**
  （`shared/contracts/plan-quota.ts`）。
- Plus は生成品質の向上とチラシ活用を価値として提示している。
- Plus 価格は **月額 580 円（税込）**、**年額 5,800 円（税込）**、**7 日間の試用**あり
  （`src/features/billing/checkout-interval-form.tsx`）。
- `PLUS_LP_UPGRADE_COMING_SOON=true` により、現在は UI と API の双方で申込を停止して
  いる。**決済導線自体は実装済みである。**
- 商用判断に使える analytics は未導入。
- OpenRouter 利用料が主な変動費である。

### 1.2 現状からの含意

- **事実**: 売上ゼロの状態は、計測基盤が無いからではなく、申込をフラグで停止している
  からである。したがって最短の学習経路は「計測を作ってから売る」ではなく
  「小さく売って実データを得る」である。
- **推測**: Plus は既存の上限差・品質差から価値仮説を説明しやすい。一方、申込停止中で
  商用 analytics もないため、現時点で転換率や継続率を事実として述べることはできない。
- **要確認（重大）**: Plus 増分 AI 原価が未実測である。Plus は月最大 300 生成
  （10 回/日 × 30 日）であり、手数料控除後の受取は約 555 円。**1 生成あたり約 1.85 円を
  超えると、上限まで使う利用者は赤字になる。** これは採算の精度ではなく、事業の符号の
  問題であり、他のどの計測よりも先に確定させる。

### 2.2 成果報酬リンクを保留にする理由と復活条件

初版は料率を列挙したが、収益の上限を一度も計算していなかった。粗い参考試算（**推測**）:

- 楽天の食品 4%、客単価 5,000 円と仮定して 1 成果あたり約 200 円。
- ただし献立を立てる利用者の買い物は基本的に実店舗であり、買い物リストから Amazon /
  楽天のネットスーパーへ流れる割合は低いと見込まれる。
- 結果として、利用者あたりの月次期待収益は**数円のオーダー**にとどまる可能性が高い。

これに対するコストは、承認済み固定語彙 ID の実装、明示確認 UI、ASP 審査、規約変更の
追随、プライバシー文言、問い合わせ対応であり、**実装工数だけで見込み生涯収益を大きく
超える**。加えて、認証必須の `/shopping` を媒体として登録できるかという blocker
（§3.5）が未解消で、成立確率自体が低い。

「次点」として残すと着手を誘発するため、保留とする。**復活条件**は次をすべて満たす
場合に限る。

1. §0 の規模（MAU、買い物面の利用実績）が把握され、粗い期待収益の試算が §0 の収益目標
   に対して有意な割合を占めること。
2. 選定 ASP の最新公式資料により、認証必須面の媒体資格が満たせると確認できること。
3. Plus の採算判断（§4 Step 3）が完了していること。

## 3. 2026-08-09 時点の公式条件

以下は各公式ページを 2026-08-09 時点の判断材料として整理したもの。料率・条件は変更
され得るため、実装直前と公開後の定期確認が必要である。

### 3.1 Stripe（事実）

- Payment Links の作成・利用自体は **無料**。
- 国内カード決済手数料は **3.6%**。
- 継続課金に Stripe Billing を使う場合は **0.7%**。
- 実際の費用は決済手段、契約、返金、異議申立て等で変わり得る。

出典: [Stripe 日本の料金体系](https://stripe.com/jp/pricing)、
[Stripe Payment Links](https://stripe.com/jp/payments/payment-links)

### 3.2 国内での有料販売に必要な表示（要確認・Plus の blocker）

日本の消費者向けサブスクリプションを販売するには、**特定商取引法に基づく表記**
（販売主体、連絡先、支払時期・方法、解約条件、返金方針等）が必要であり、適格請求書
（インボイス）の扱いも整理が要る。リポジトリを確認した限り `src/` に該当する表示面は
存在せず、言及は `docs/archive/` の過去設計書のみである。

**計測がどれだけ整っても、これが無ければ 1 円も受け取れない。** 初版では §7.2 の
チャネル別前提に埋もれていたが、改訂版では Step 0 と並行して着手する最上位項目として
扱う（§4 Step 1）。

### 3.3 広告であることの表示（事実）

広告であるにもかかわらず一般消費者が広告と判別しにくい表示は、景品表示法上の
ステルスマーケティング規制の対象となる。成果報酬リンクやスポンサー表示を将来採用する
場合は、広告・収益関係が分かる表示をリンクまたは内容の近傍に置く。

出典: [消費者庁「ステルスマーケティングに関する景品表示法上の考え方」](https://www.caa.go.jp/policies/policy/representation/fair_labeling/stealth_marketing/)

- 食品・飲料の紹介料率は **8%**、キッチン用品は **3%**。
- 所定のアソシエイトである旨の必須文言、申込み後の審査、運営規約の遵守が必要。
- 紹介料率、対象カテゴリおよび審査条件は変動し得る。

出典: [Amazon アソシエイト・プログラム紹介料率表](https://affiliate.amazon.co.jp/help/node/topic/GRXPHT8U84RAYDXZ)、
[Amazon アソシエイト・プログラム運営規約](https://affiliate.amazon.co.jp/help/operating/agreement/)

### 3.5 楽天アフィリエイト（事実・保留チャネルの参考）

- 食品の料率は **4%**、キッチン用品は **3%**。
- クリック後 **24 時間以内に買い物かごへ追加**され、**89 日以内に購入**された成果が
  対象となる条件がある。
- 通常の成果報酬上限は **1 商品 1,000 円**、同一ユーザーによる購入は **月 3,000 円**。
- 料率、成果条件、上限および対象カテゴリは変動し得る。

## 4. 実行順序（改訂の中心）

初版は、売上ゼロの段階で集計設計（Phase 0A）と計測実装（Phase 0B）を人間承認つきの
独立 Task として先行させ、実課金までにゲートを 6 つ置いていた。改訂版では次の 3 点を
理由に順序を入れ替える。

1. 採算の符号を決める AI 原価は、analytics なしで今日測れる。
2. 申込停止中の CTA クリック率は「行き止まりのボタンのクリック率」であり、購入意思では
   なく好奇心の計測にすぎない。同じ工数で実課金を限定解放すれば、**実際の支払い**という
   比較にならない強度の信号が得られる。加えて、押しても進めない導線は体験を損なう。
3. 国内販売に必要な表示（§3.2）は、計測の完成度と無関係に課金の前提となる。

### Step 0 — 原価と規模の実測（次 Task、実装しない）

- **実証内容**: OpenRouter の課金実績と生成ログから、生成 1 回あたりの実測 AI 原価
  （Free 基準原価と Plus 増分）を算出する。あわせて §0 の MAU・上限到達者数・収益目標を
  確定する。
- **判断**: 1 生成あたり原価が §1.2 の分岐点（約 1.85 円）に対してどこに位置するか。
  - 十分に下回る → 現行の 580 円 / 10 回/日 のまま Step 2 へ。
  - 近接または上回る → 価格改定、上限見直し、または従量アドオンへの切り替えを
    Step 2 の前に決める。
- **停止条件**: 信頼できる原価の正本を得られない場合、限定解放に進まない。

### Step 1 — 販売の法的前提（Step 0 と並行）

- **実証内容**: 販売主体、特定商取引法に基づく表記、返金・解約運用、税務上の取扱いを
  確定し、表示面を用意する。
- **停止条件**: 未確定のまま課金を再開しない。

### Step 2 — 最小計測 + 限定 pilot（Step 0/1 の後）

初版の Phase 0A / 0B / 1A / 1B を 1 つに統合する。**限定 pilot を安全に回すために最低限
必要な計測だけ**を実装し、精緻な定義は実データを見てから固める。

- **最小計測の範囲**: Stripe とサーバーを正本とする checkout 開始、試用開始、有料開始、
  返金・chargeback、AI 原価、Free 上限到達数。client event は参考指標にとどめ、client の
  申告だけで売上、原価、quota を決めない。
- **先に固定する定義（要決定）**: 税込／税抜、gross と net、返金・chargeback の計上時点、
  月額と年額の期間按分、Plus 増分 AI 原価の配賦、各費用を全体で一度だけ計上する規則。
  cohort key と成熟条件は、§0 の規模が小さい場合は簡素化してよい。
- **プライバシー原則（初版から維持）**: 契約・請求に必要な billing operational data と、
  判断用の analytics 出力を分離する。analytics に識別可能な個票を残さない。保持期間、
  削除要求時の扱い、閲覧権限は実装前に確定する。
- **実証内容**: `PLUS_LP_UPGRADE_COMING_SOON` による UI / API の停止を、事前に定めた
  限定対象だけに整合して解放し、実際の支払いを観測する。
- **要決定**: 限定対象、開始・終了条件、判定期間、利用者への説明、UI と API を同時に
  再閉鎖する即時条件。
- **KPI 式（要決定）**:
  - `有料転換率 = 成熟した試用開始 cohort のうち有料開始した件数 ÷ 同 cohort の試用開始数`
  - `Plus 単位寄与 = 同一認識期間の gross − 決済・Billing 手数料 − 返金・chargeback − Plus 増分 AI 原価 − 配賦費用`
- **即時再閉鎖条件**: 課金・entitlement の不整合、誤請求、削除・プライバシー境界の破綻、
  原価の異常、または人間が定める安全・採算条件への抵触。具体的な条件は pilot 前に
  **要決定**。

### Step 3 — 一般解放／継続／撤退

- **判断**: 成熟した pilot cohort の転換、継続、返金・chargeback、Plus 単位寄与、運用
  負荷を基に、一般解放、pilot 継続、価格・課金モデルの変更、再閉鎖のいずれかを決める。
- **KPI 式（要決定）**:
  - `継続率 = 必要な観測期間を満たした有料開始 cohort のうち継続条件を満たす件数 ÷ 同 cohort の有料開始数`
  - `全体純寄与 = Plus 純寄与 + 単発支援純寄与`（成果報酬は保留中のため計上しない）
- **配賦原則**: Free 基準 AI 原価、Plus 増分 AI 原価、共通費、一時費を Step 2 で定めた
  規則で一度だけ計上し、チャネル合算時に二重控除しない。
- **停止条件**: 純寄与が §0 の目標に対して人間の定める閾値を満たさない、または献立支援
  という製品目的より収益導線が優先される場合は、そのチャネルから撤退する。閾値と判定
  期間は**要決定**。

### 参考: Plus の簡易採算式

> Plus 売上寄与 = 会員数 × 価格 − 決済・Billing 手数料 − AI 原価 − 返金等

「価格」は手数料控除後の受取額ではなく、表示価格の gross を指す。月額と年額を分け、
同じ売上認識期間へ按分し、税込／税抜を統一する。Free 基準原価ではなく Plus 増分 AI
原価を一度だけ控除する。

国内カード **3.6%** と Billing **0.7%** を価格に単純適用した参考値:

- 月額 580 円: `580 × (1 − 0.036 − 0.007) ≒ 555 円`
- 年額 5,800 円: `5,800 × (1 − 0.036 − 0.007) ≒ 5,551 円`

これは**採算や入金額の確定値ではない**。税の会計上の扱い、返金、異議申立て、固定の
追加費用、決済手段差、試用、実際の AI 原価その他の実コストを除外した参考計算である。
これらを織り込まずに価格や利益を決めてはならない。

## 5. 成果報酬リンクの不変条件（保留チャネル・復活時に有効）

§2.2 により当面は着手しないが、将来復活させる場合の設計上の不変条件として保存する。

1. 買い物リスト全体を外部へ自動送信しない。
2. 手入力または編集済みの文字列は、検査や明示確認の有無にかかわらず、動的外部送信の
   対象へ昇格させない。
3. 買い物項目由来で外部へ渡せる動的検索語は、サーバー管理の承認済み固定語彙 ID から
   導出する不変の単一検索語だけとする。未知の ID、語彙との不一致、長さ・制御文字等の
   完全性検証への不合格は fail-closed で拒否する。未知の自由文を機微語検出によって許可
   する代替経路は設けない。
4. 外部送信の直前に、実際に送る文字列と遷移先 ASP をユーザーへ表示し、明示確認後の
   クリックでのみ送信する。
5. 固定リンク方式を使う場合も、選定 ASP が公式に許可したリンクだけに限定する。
6. 遷移先は固定した HTTPS の origin と path の allowlist に限定し、検索語は標準的な
   query encoding を用いて安全に組み立てる。ASP 公式方式が許可しない URL 改変、任意の
   redirect、ユーザー入力 URL への遷移を許可しない。
7. 外部遷移であること、および広告・収益リンクであることをリンクの近傍に表示する。
8. 検索語と完全な遷移 URL を、アプリケーションログや analytics のイベントに保存しない。
9. 第三者 JavaScript や計測ピクセルを組み込まない。
10. 商品価格・商品画像・商品 API の利用は含めず、採用前に各社規約を別途確認する。
11. プライバシー文言と、法令・送信内容・利用サービスに照らして必要となる同意を、実装前
    に確定する。

成果報酬は、購入時点の表示金額をそのまま計算基礎にしない。Amazon は ASP が確定した
適格収入 × 適用料率を基礎とし、不適格注文、返品、返金等を除外する。楽天は商品・
同一ユーザーの上限、否認、取消等を反映した ASP の確定成果報酬を正本とする。いずれも
ASP の確定値を超える収益予測は行わない。
