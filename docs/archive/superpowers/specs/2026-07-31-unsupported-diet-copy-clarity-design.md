## 1. 背景と問題

### 1.1 選択肢の意味が分からない

家族メンバーの追加・編集で「食べない食事はありますか」を「該当あり」にすると、次の3項目が出る。

- 離乳食
- 飲み込み・むせの不安
- 医師等から指示された治療食

利用者から見て意味が取りにくい。

| 表示 | 誤解されやすい点 |
|---|---|
| 離乳食 | 「食べない食事」の選択肢に見える。実際は「離乳食が必要な段階」 |
| 飲み込み・むせの不安 | 何を選ぶ項目か曖昧。実際は「飲み込み・むせに不安がある」事情 |
| 医師等から指示された治療食 | 指示内容を書く場所がない。実際は詳細入力の対象ではなく、このアプリでは作れないことの申告 |

### 1.2 「該当あり」後も設定を続ける意味が不明

仕様上、`unsupported_diet_status = present` のメンバーは **通常の AI 献立の対象にならない**（設計書 §6）。  
そのメンバー向けに献立を「作る」意味はない。登録の意味は次に限られる。

1. 誤って生成対象に入れない安全ゲート  
2. 「この人には作らない」という明示的な記録  
3. 他メンバー向け献立を使う世帯での名簿管理  

現状はフォーム途中で初めて「通常の献立では対応できません」と出るため、**追加操作の入口では伝わらない**。

### 1.3 原因

設計上の概念は **「このアプリが通常献立として対応できない食事の事情」**（`unsupported_diet_*`）である。

- 設計書 `2026-07-11-kondate-mvp-design.md` §6: 対象外確認状態・対象外種別。該当ありのメンバーは通常生成の対象にしない
- UI refresh（`2026-07-21-ui-refresh-design.md`）で親質問を「対象外の食事の確認」→「食べない食事はありますか」へ平易化した結果、親質問と選択肢の意味軸がずれた

治療食の指示内容を保存・生成に使う機能は **意図的に存在しない**（MVP スコープ外: 離乳食・嚥下調整・治療食は生成しない）。

## 2. 目標

1. **家族を追加する前**に、対象外の事情がある方の**個人向け**メニューには対応していないこと、他の家族向けは使えること、それでも登録する場合は「この人には作らない」明示であること、を伝える
2. 親質問・選択肢・説明文が同じ意味軸（離乳食・飲み込み不安・治療食の3種＝このアプリで作れない事情）で揃う
3. 3選択肢が「食べない料理」ではなく「事情・必要」として読める
4. 治療食について「指示を書く欄がない」理由が画面上で分かる
5. アレルギー／苦手との混同を親質問レベルで防ぐ
6. データ構造・生成拒否・検出ロジックは変えない

## 3. 非目標

- `unsupported_diet_status` / `unsupported_diet_kinds` の enum・DB・RLS 変更
- 治療食・離乳食・嚥下向けの献立生成や、指示内容の自由記述フィールド追加
- `medical-scope` 検出語・`unsupported_diet` 生成エラーコードのキー変更
- 「苦手食材」など別機能の文言変更
- 「該当あり」選択時にアレルギー等の入力項目を自動スキップする大規模フロー変更  
  （登録は名簿＋対象外明示のまま。入力簡略化は本変更の対象外）
- planner / 生成結果の拒否コピーの全面改訂（入力面・追加前ダイアログに限定。必要なら別チケット）

## 4. 製品判断（固定）

| 判断 | 内容 |
|---|---|
| present の意味 | そのメンバー向けの通常献立は **作れない**。生成対象から外す |
| 登録を許す理由 | 「この人には作らない」明示として名簿に残せる。他メンバー向け利用は可能 |
| 入口 | フォーム内の後追い説明だけでは不足。**追加操作の直前**に確認ダイアログを出す |
| 編集 | 既存メンバー編集ではダイアログを出さない（追加時のみ）。フォーム内の事情フィールドと present 説明で担保 |
| スコープ語 | 「食事の事情」単独では使わず、**3種別（離乳食・飲み込みの不安・治療食）に限定した事情**として表記する |

## 5. 追加前確認ダイアログ

### 5.1 トリガー

次の操作で、**下書き作成（`createDraft` / オンボーディングの startMutation）を呼ぶ前**にダイアログを開く。

| 画面 | 操作ラベル |
|---|---|
| 家族設定（空状態・一覧） | 家族を追加 |
| オンボーディング（未開始） | 家族設定を始める |
| オンボーディング（1人完了後の次アクション） | 続けて家族を追加 |

- **登録を続ける（OK）**: ダイアログを閉じ、従来どおり下書き作成 → 入力フォームへ  
- **やめる** / **Escape**: ダイアログを閉じるだけ。ネットワーク呼び出しなし  
- 編集ボタン・既存 draft 再開では出さない  
- 1 セッション中に何度追加しても、**追加のたびに**出す（「一度見たら出さない」はしない。対象外の説明は毎回重要）

### 5.2 確定文言

| 箇所 | 文言 |
|---|---|
| 見出し | 登録の前に |
| 本文（個人スコープ） | 当てはまる方がいる場合、その方個人向けのメニューには対応していません。他の家族向けの献立はこれまでどおり作れます。 |
| 箇条書き（`ul`/`li`） | 離乳食が必要 / 飲み込み・むせに不安がある / 医師等から治療食の指示がある |
| 補足 | それでも登録する場合は、「この人には献立を作らない」という明示として名簿に残せます。通常の献立の対象にはなりません。専門職の指示に従ってください。 |
| 主ボタン | 登録を続ける |
| 副ボタン | やめる |

### 5.3 UI / a11y（必須・削除確認と同等）

既存の家族削除確認（`household-settings-page.tsx` の delete dialog）と同系統を **次の項目まで**必須とする。

1. `role="dialog"` + `aria-modal="true"` + バックドロップ（`pantry-expired-dialog-*` または同等）
2. 見出し契約: 可視見出し（例: `h2`）に `id` を付け `aria-labelledby` で結ぶ、**または** `aria-label="登録の前に"`。ページ内でどちらか一方に統一
3. 箇条書きは意味のあるリスト（`ul` / `li`）
4. 主・副ボタンは最小 44×44 CSS px
5. 開いたとき主ボタン「登録を続ける」へフォーカス
6. 閉じたあと: **そのダイアログを開いたトリガー要素**へフォーカスを戻す（trigger を open 時に記録。settings の `deleteTrigger` と同型）
7. **Escape** で閉じる（副ボタンと同等。ネットワークなし）。作成中（OK 後の mutate pending）は Escape で閉じない／または閉じてもよいが二重 mutate は禁止（下記 single-flight）
8. **背面（backdrop）click では閉じない**（削除確認踏襲）
9. 主ボタン経路は **single-flight**: settings は既存 `creatingDraftRef`、onboarding は `startMutation.isPending` 等。OK 連打で `createDraft` / start を二重に呼ばない
10. 320 CSS px 幅で横スクロールなし。色だけに依存しない

### 5.4 状態

- クライアントローカル state のみ（例: `addScopeNoticeOpen`）。DB 永続化しない  
- ダイアログ表示中は背面の「家族を追加」等を操作不可（modal）
- OK 後に status を `present` へ自動設定しない（§7）

## 6. フォーム側の確定文言

| 箇所 | 現行 | 変更後 |
|---|---|---|
| 親質問（label / aria-label） | 食べない食事はありますか | 離乳食・飲み込みの不安・治療食など、このアプリで献立を作れない事情はありますか |
| 親質問の直下ヘルプ（常時） | （なし） | アレルギーや苦手なものは別の項目です。ここでは上の3つだけを答えます。 |
| 親の選択肢 | 該当なし / 該当あり / 未確認 | **据え置き** |
| fieldset 見出し（legend） | 該当する項目 / 食べない食事 | 該当する事情 |
| `weaning_food` | 離乳食 | 離乳食が必要 |
| `swallowing_concern` | 飲み込み・むせの不安 | 飲み込み・むせに不安がある |
| `therapeutic_diet` | 医師等から指示された治療食 | 医師等から治療食の指示がある |
| present 時の説明文 | 通常の献立では対応できません。…（onboarding のみ） | 選んだ場合、このメンバー向けの通常の献立は作れません。対象から外すか、専門職の指示に従ってください。治療食の指示内容はここでは入力できません（このアプリでは作れないためです）。 |
| 未確認時メッセージ | 食べない食事を確認するまで、このメンバーは献立生成に使えません。 | 作れない事情を確認するまで、このメンバーは献立生成に使えません。 |
| バリデーション（status 未選択） | 食べない食事があるか選んでください | 作れない事情があるか選んでください |
| kinds 空 | 該当する項目を選んでください | 該当する事情を選んでください |
| オンボーディング導入文 | 年齢のめやす、アレルギー、食べない食事の3項目から始めます。 | 年齢のめやす、アレルギー、作れない事情の3項目から始めます。 |
| 空状態ヘルプ（settings） | 「家族を追加」を押すと、1人目の入力が始まります。… | 「家族を追加」を押すと、登録の前に確認が表示されます。続けたあと、1人目の入力が始まります。呼び名・年齢・アレルギーなどを順に入れられます。 |
| superRefine 矛盾メッセージ | 対象外状態と項目を確認してください | **据え置き**（内部整合用） |

status の `none` / `present` / `unconfirmed` の表示語は変更しない。

フォーム内の present 説明は、追加前ダイアログと矛盾しないよう **「このメンバー向けの通常献立は作れない」** を明示する。

## 7. 挙動（不変）

- `none`: そのメンバーは通常生成の対象になり得る（他条件を満たす場合）
- `present` + 1 つ以上の kind: そのメンバーは通常生成の対象外
- `unconfirmed`: 確認するまでそのメンバーを含む AI 献立を生成しない
- kind の選択は「事情の申告」であり、献立内容への細かい調整指示ではない
- ダイアログの OK は status を `present` に自動設定しない。利用者はフォームで該当なし／あり／未確認を選ぶ

## 8. 実装方針

### 8.1 表示コピーの単一ソース

現状、kind ラベルとバリデーション短文が二重定義されている。

- `household-onboarding-page.tsx` の `unsupportedDietOptions` および complete 前ローカル validate メッセージ
- `household-settings-page.tsx` の `unsupportedDietKindLabels`
- `household-settings-schema.ts` の Zod メッセージ

**同じディレクトリ内の共有定数**（例: `unsupported-diet-copy.ts`）に寄せる。

含めるもの:

- 親質問、親ヘルプ、kind ラベル、fieldset 見出し、present 説明、未確認メッセージ、バリデーション短文（status / kinds）
- 追加前ダイアログの見出し・本文・箇条書き配列・補足・ボタン文言
- 空状態ヘルプ、オンボーディング導入文

**onboarding の complete 前ローカル validate も同一定数を import する**（schema と文字列リテラルを二重に持たない）。schema の Zod メッセージも同定数を参照する。

ブラウザ境界（`src/features/household`）内に閉じ、`shared/` や Netlify Functions へは出さない。

### 8.2 変更対象ファイル（固定・「ほか」禁止）

| 種別 | パス |
|---|---|
| 新規 | `src/features/household/unsupported-diet-copy.ts` |
| 本番 UI | `household-onboarding-page.tsx`, `household-settings-page.tsx` |
| スキーマ | `household-settings-schema.ts`（status 未選択・kinds 空メッセージ） |
| 単体テスト | `household-onboarding-page.test.tsx`, `household-settings-page.test.tsx`（追加直後 createDraft assert・文言・ダイアログ開閉・編集では非表示） |
| E2E fixture | `e2e/fixtures/auth.ts`（`completeMinimumOnboarding`）, `e2e/fixtures/history.ts`（`openFirstMemberEditor` の追加分岐） |
| E2E specs | `e2e/specs/onboarding.spec.ts`, `e2e/specs/settings.spec.ts`, `e2e/specs/menu-domain-pantry.spec.ts` |

E2E は **推奨**: `e2e/fixtures/household.ts` 等に `confirmAddScopeNotice(page)` を1関数置き、「登録を続ける」クリックを集約する。上記必須ファイルはすべてそのヘルパーまたは同等1ステップを通す。

settings の present 時 fieldset に、onboarding と同じ説明文を追加する。  
「押すとすぐ開始」系の空状態ヘルプは §6 表どおり更新する。

### 8.3 変更しないもの

- `shared/contracts/domain.ts` の英語キー
- `shared/safety/medical-scope.ts`
- 生成エラーコードキー
- DB マイグレーション・generated types
- 削除確認ダイアログの既存文言（本機能と独立）
- planner / generation の拒否コピー（§3 非目標）

## 9. テスト方針

1. **追加前ダイアログ**
   - トリガー操作で dialog が開く
   - 開いた時点では `createDraft` / start が呼ばれていない
   - 「やめる」および Escape で閉じ、API 未呼び出し
   - 「登録を続ける」で閉じ、従来どおり下書き作成が走る
   - OK 連打でも createDraft / start は1回
   - 編集開始では出ない
2. **文言**: 新 label / checkbox name / 説明文 / 空状態ヘルプで要素を引く
3. **旧文言ゼロ確認（範囲固定）**
   - **必須ゼロ**: `src/features/household/**` 内のユーザー向け文字列（本番 TSX、schema、共有 copy、テストの getByLabel / 期待文字列）
   - **意図的残置**: `docs/**`（本設計・UI refresh 履歴・レビュー）、planner / generation の拒否コピー（§3）、コードコメントは新語に合わせてよいがゲート対象外
4. **schema / onboarding validate**: 共有定数のメッセージが両方から使われること
5. **E2E**: §8.2 必須リストの全経路。追加操作の直後に「登録を続ける」を踏んでからフォーム操作
6. **回帰**: kind の保存値は `weaning_food` 等のまま

検証コマンド（Docker、スコープ実行・コマンド連結禁止）:

```bash
docker compose run --rm --no-deps app npx vitest run src/features/household/
docker compose run --rm --no-deps app npm run typecheck
docker compose run --rm --no-deps app npm run lint
docker compose run --rm --no-deps app npm run format:check
```

E2E は実装計画の該当 Task で §8.2 の fixture/spec を実行する。

## 10. リスクと緩和

| リスク | 緩和 |
|---|---|
| 毎回ダイアログが冗長 | 対象外は安全上の重要情報。スキップ設定は入れない（本設計の固定） |
| E2E が追加ボタン直後にフォームを期待して落ちる | §8.2 必須ファイルをすべて更新。ヘルパーで「登録を続ける」を集約 |
| 親質問・ダイアログが長く 320px で崩れる | 既存 dialog / field スタイルで折り返し。横スクロール禁止を維持 |
| ダイアログとフォームの二重説明 | 入口は「個人向け非対応＋他家族は可＋名簿明示」、フォームは「該当あり＝この人向けは作れない」で役割分担 |
| 編集で none→present | 追加時ダイアログは出ない。**フォームの present 説明文で担保**（本設計の固定） |
| UI refresh 設計書との文言差分 | **入力面・追加前 UX の文言は本設計が優先**。UI refresh 表は歴史記録。矛盾時は本設計を正とする |

## 11. 成功条件

- 家族追加の直前に、対象外事情・個人向け非対応・他家族は可・「作らない明示としての登録」が読める
- 親質問がアレルギー／苦手と混同されにくい
- 「該当あり」時の3項目が事情として読める
- 治療食について、指示を書く欄がない理由がフォーム説明で分かる
- enum キー・DB・生成拒否は変更前後で同一
- `src/features/household/**` の旧入力面文言がゼロ
- 対象単体テストと §8.2 E2E が新フロー・新文言で通る
